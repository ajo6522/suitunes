Suitunes V1 — Versioned Feature Specification and
Implementation Documentation
Specification version: Suitunes V1.0.0-dev-spec
Document status: Development single source of truth
Date: November 4, 2026
Primary implementation: C++ / JUCE
Primary test host: FL Studio
Initial plug-in targets: VST3 on Windows and macOS; Audio Unit on macOS
Product principle: Suitunes is a vocal pitch-correction plug-in built around two deliberately different
workflows: Auto Tune for immediate real-time correction and Fine Tune for a friendlier , simplified offline
pitch editor . It should not attempt to reproduce every capability of NewTone or Melodyne.
Executive summary
Suitunes V1 should be developed as two related pitch-correction systems sharing one musical model,
preset/state system, and visual language. Auto Tune processes a monophonic vocal in real time,
determines the singer's fundamental pitch, chooses an allowed target according to key/scale or incoming
MIDI, smooths the requested correction, then applies a pitch shift while attempting to preserve vocal
character . Fine Tune analyzes a recorded WAV, turns the vocal into visually understandable note regions
and pitch curves, and lets the user automatically correct either a highlighted region or the entire vocal with
a prominent Auto Fine Tune command. Users who want intervention can drag notes vertically, split a
detected note, and undo their edits, but the interface is intentionally less precise and less tool-heavy than
NewTone.
This division mirrors a well-established distinction in commercial pitch products. Image-Line describes
Pitcher as a real-time pitch-correction/manipulation plug-in and NewTone as the related detailed editing
tool. Pitcher also documents MIDI-controlled target pitches, correction-speed behavior , monophonic-source
requirements, and formant preservation, while NewTone exposes note blocks, a detected continuous pitch
line, note splitting, selections, and audio-to-MIDI-style score output.  Suitunes should adopt the 
workflow lessons from those tools without copying their UI.
The strongest first implementation candidate for real-time pitch shifting is Signalsmith Stretch. It is a C++
library under the permissive MIT license, exposes input/output latency explicitly, supports continuously
changing pitch, and provides formant-related controls. Its current header identifies version 1.3.2, and the
repository was active in October 2026. Rubber Band 4.0 is technically mature and has a dedicated 
RubberBandLiveShifter, but its own documentation states that live-shifter delay is typically 50 ms or
more, making it unsuitable as the first choice for a low-latency tracking mode; proprietary distribution also
requires a commercial license unless Suitunes itself complies with the GPL. SoundTouch is mature and
can run in real time, but its time-stretch path documents latency of roughly 100 ms, so it should be retained
as a benchmark/fallback experiment rather than the default real-time vocal engine.

For pitch detection, the first prototype should implement YIN directly and simultaneously benchmark 
aubio YIN/YINFFT as a reference. The original YIN paper describes a relatively simple F0 estimator
designed for speech and musical signals that can be implemented efficiently and with low latency. 
aubio conveniently provides yin, yinfft, yinfast, and several other estimators, but its code is
GPLv3-or-later , so it should not be embedded into a closed-source commercial Suitunes binary without
an appropriate commercial licensing arrangement.  The cleanest initial architecture is therefore an
in-house YIN implementation used in the shipping path, with aubio serving as a development-time
comparison oracle unless licensing is resolved.
The real-time goal needs to be treated as an engineering target, not a promise. Antares' current
documentation provides useful competitive context: its low-latency modes are reported at approximately 
0.77 ms to 2.3 ms at 48 kHz, depending on mode, and the company recommends slower correction times
for more natural vocal behavior .  Suitunes V1 should initially define a recommended engineering
target of ≤10 ms reported plug-in algorithmic latency, with ≤15 ms as the provisional V1 ceiling,
while measuring complete monitored round-trip latency separately. This target was not specified by the
user and must be considered provisional until prototype measurements show what is technically realistic.
At 48 kHz, 10 ms corresponds to 480 samples and 15 ms to 720 samples. At 44.1 kHz the same thresholds
are approximately 441 and 662 samples, and at 96 kHz they are 960 and 1,440 samples. A host must be
told the true algorithmic delay: JUCE exposes AudioProcessor::setLatencySamples(), VST3 requires
processors to report group delay in samples, and FL Studio can automatically compensate correctly
reported plug-in latency. 
The most important development rule is therefore: prove the pitch engine before polishing the full
product. The first experiment should be a stripped-down JUCE VST3 using direct YIN + Signalsmith Stretch,
instrumented for pitch error , correction latency, CPU use, and glitches. If that engine does not meet the
provisional latency and quality targets, the architecture should permit swapping in another shifter without
rewriting the musical logic or UI.

Speed is conceptually analogous to correction/retune speed in established tools: faster settings move the
output toward the allowed pitch more aggressively, while slower settings preserve more of a singer's slides
and legato behavior . Image-Line documents the same tradeoff for Pitcher , and Antares recommends slower
retune values for natural correction and faster values for harder tuning.  The precise numerical range
and knob mapping for Suitunes are unspecified and should not be frozen until listening tests.
Correction Strength is a Suitunes-level control rather than a direct library parameter . It should interpolate
between no correction and the full target trajectory generated by the tuning engine. Whether the UI
exposes continuous 0–100%, named levels, or both is unspecified.
MIDI Control changes the target-note source. Incoming MIDI notes should override or constrain normal
scale targeting according to a clearly defined mode. This is established behavior in Pitcher and Auto-Tune;
Antares explicitly documents incoming MIDI as pitch targets, and Image-Line documents playing Pitcher's
corrected target from a MIDI keyboard or piano roll. No-MIDI behavior must be explicit:
recommended V1 behavior is to bypass correction while MIDI Target mode is enabled and no target note
exists, matching the current Antares behavior; this is a recommended design choice, not a user-specified
requirement.

Required detector conditions: silence must not produce a valid target; unvoiced consonants should

the project must benchmark rather than assume superiority.

Signalsmith documents separate input and output latency and explains how automation should be aligned
with the internal processing time. It also supports formant compensation and recommends providing a
rough fundamental-frequency estimate for its formant behavior—information Suitunes' detector can supply
directly. 
Rubber Band 4.0's live shifter is explicitly designed as a simpler pitch-only API and is real-time safe in the
sense of avoiding allocation, locking, and blocking in the normal processing path, but the official API
documentation warns that its delay remains 50 ms or more.  That essentially rules it out as the initial
"feels like Pitcher" tracking engine even though it may be valuable for the offline Fine Tune renderer .
SoundTouch's own documentation places normal time-stretch processing near 100 ms latency and
describes its core time-domain process as WSOLA-like.  That is substantially above the proposed
Suitunes live target.

duration, breath detector , and transition rules are unspecified and must be tuned against vocal datasets.

Apple documents Audio Units as the native plug-in architecture and supports Audio Unit processing and

For VST3, MIDI note messages arrive through VST3 event buses rather than a legacy raw MIDI stream;
Steinberg maps MIDI Note-On/Note-Off concepts to VST3 NoteOnEvent and NoteOffEvent.  JUCE's
MidiBuffer abstraction should shield most of this format-specific handling from the DSP layer .
FL Studio MIDI routing
FL Studio's wrapper exposes plug-in MIDI input/output ports and permits matching port numbers between
MIDI-generating channels and a plug-in.  Pitcher's own FL Studio documentation uses this exact model
to route MIDI from a MIDI Out channel into Pitcher .  Therefore FL Studio acceptance testing must
include:
Suitunes instantiated as a mixer effect.
MIDI input enabled in the VST3 build.
FL wrapper input port configured.
MIDI Out generator configured to the matching port.
Note-On/Note-Off verified sample-accurately enough for tuning.
Held-note and no-note behavior verified.
MIDI automation tested during playback and recording.
MIDI import and MIDI control
MIDI import should accept at minimum Standard MIDI File Type 0 and Type 1. The MIDI Association
describes Standard MIDI Files as time-stamped event files and identifies Type 0 and Type 1 as the common
file forms. 
When imported into Fine Tune, MIDI may be used as a target melody. The exact UI for mapping a MIDI
track to the vocal is unspecified. Recommended V1 behavior is to read the first nonempty note track by
default while providing a track picker if multiple note tracks exist.

Audio-thread rules
processBlock() is an audio-thread callback and JUCE explicitly warns against UI interaction from it. 
The audio path must therefore:
perform no file I/O;
perform no JSON/XML parsing;
avoid locks and blocking synchronization;
avoid dynamic allocations in steady state;
never call AudioProcessorValueTreeState::copyState() or replaceState() inside the
callback because JUCE documents them as locking and not real-time safe; 
preallocate all large buffers in prepareToPlay();
use lock-free or atomically readable control state between UI/control threads and DSP;
post display information to the UI through a ring buffer or atomic snapshot.
JUCE notes that resizing AudioBuffer can cause allocation, so processing buffers should be prepared for
the host's advertised maximum block size rather than expanded inside normal audio callbacks.

Parameter smoothing
Any rapidly changing parameter that affects signal amplitude, pitch ratio, wet mix, or formant behavior
must be smoothed. JUCE's SmoothedValue is explicitly intended to avoid glitches from abrupt value
changes and supports linear and multiplicative smoothing.  JUCE's own plug-in tutorial likewise
demonstrates gain ramping to prevent discontinuity clicks. 
Recommended rules:
pitch ratios: multiplicative/log-domain smoothing;
wet/dry/gain: linear smoothing;
Speed: modifies the target trajectory rather than itself requiring sample-rate interpolation;
Correction Strength: smooth changes over a short ramp;
key/scale changes: crossfade or defer target reassignment to avoid instantaneous pitch
discontinuities;
MIDI target switches: allow fast but nonzero transition unless hard-tune mode intentionally
demands immediate transitions.
Exact smoothing durations are unspecified.
Buffering
Support host block sizes at least 16, 32, 64, 128, 256, 512, 1,024, and variable block sequences. FL Studio's
wrapper documentation confirms that hosts may use variable-size chunks and provides a compatibility
option for plug-ins that improperly require fixed buffers.  Suitunes should not depend on FL Studio's
fixed-buffer workaround.
Internal pitch-analysis hop sizes may differ from host blocks. A ring-buffer architecture should accumulate
exactly the analysis window required by YIN and emit pitch estimates at a fixed hop independent of host
callback boundaries.
Plug-in latency reporting
At prepare/configuration time:
constintalgorithmicLatencySamples= engine.getLatencySamples();
setLatencySamples(algorithmicLatencySamples);
JUCE directs processors to call setLatencySamples() so the host knows the imposed delay.  VST3
defines this latency as processor group delay and requires hosts to be notified if it changes. 
Avoid changing the reported latency while transport is running unless absolutely necessary because the
host may need to recompute compensation, potentially interrupting playback.  Prefer fixed latency per
quality/mode setting.

treated as an aspirational external benchmark, not a guaranteed Suitunes V1 requirement.
FL Studio latency procedure
Use a project at 48 kHz and repeat at 44.1/96 kHz.
Route a sample-accurate impulse or sharp transient to a dry track and an identical Suitunes-
processed track.
Disable correction or configure a unity/no-pitch-shift case while keeping the engine active.
Render both tracks.
Measure sample offset between input and processed waveform.
Compare measured offset to Suitunes' getLatencySamples().
Verify FL Studio's wrapper displays the expected reported latency.
Enable Automatic Plugin Delay Compensation and verify the rendered processed track aligns with
the dry reference.
Repeat at host buffer sizes 32/64/128/256/512/1024 where supported.

measure end-to-end latency.

latency to maintain mixer-track synchronization.
